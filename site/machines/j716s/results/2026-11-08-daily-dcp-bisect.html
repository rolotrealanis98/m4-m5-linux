The first daily with the DCP driving the panel fell back twice (see the first-boot result). A nine-boot unattended bisect found why. Every payload differs from the failed twin in one part; stage 1's 150 s watchdog and the A/B fallback were the safety net, and the daily was restored after each series.

Root cause #

dt_set_display_t6050() in the loader re-finds the display nodes by phandle and bails with "DCP: T6050: a display node has no phandle" when dcp or display-subsystem has none. dtc emits a phandle only for nodes some property references; the in-tree J716s DT labels both nodes but only extends them (&dcp { ... }), so the in-tree DTB has no phandle on either (the stage C DTB, built differently, has 0xd3 and 0xd4). The bail makes kboot_prepare_dt() fail, stage 2 prints "Failed to prepare FDT!" and drops into the proxy; with no host attached nothing feeds the watchdog, and the stage-1 150 s dog resets the machine. That fits every boot: with the display hand-off and the in-tree DTB everything fell back; without the hand-off (B1, B3) or on the stage C DTB (B5) everything booted.

Fix #

A loader patch gives any display node without a phandle a new one (highest offset first); the same change is pushed to omacom/m1n1 #35. With the two phandles in the DTB the DCP boots on the in-tree device tree (B4 above).

Not tested #

GPU and DCP together on this fix (the next result). No console capture exists for the first fallbacks: iBoot clears the crash-log region on every boot.
